## 0. 一句话定位

**一个只排计划的 AI 教练。**

不做动作指导（不教动作怎么做），不做训练记录（训记负责记录与执行）。只做两件事：**排下周计划** + **周期复盘**。

**最根本目的（用户原话）**：
> 我自己训练其实也可以进步，但可能进步得没那么快。我希望有一个 AI 能根据我的总结，让我们能够**更快速**地进步，然后**更加全面、更加科学**地训练。**这就是最根本的目的，一切围绕这个为中心。**

## 1. 核心闭环：两条线，构成一个循环

### 线 1 · 制定计划

```
读（身体数据 + 周期目标 + 本周特殊情况 + 训练画像 + 上周变化）
  → 生成本周计划（周几练什么、组数次数重量）
  → 我在写入前调整（整个训练日模块拖到另一天）
  → 确认 → 导入训记
  → 我执行
```

### 线 2 · 复盘

```
系统读回实际完成情况（训记里未完成的会体现，如某动作只完成 50%）
  → 手账式页面：上=实际训练表格，下=我写的感受（每天可写）
  → 一周结束后，点「AI 复盘」
  → 输出简短复盘（达标吗 / 完成率 / 下周微调建议）
  → 结论进入下周计划的输入
```

### 交汇点

**复盘的结论 → 下周计划生成的参考输入。** 两条线在这里闭合成环。

**为什么按周复盘**：一个月复盘一次肯定想不起来；每天复盘又太繁琐。折中方案：**感受每天可写，总结每周一次。**

## 2. 四个页面

### ① 首页 · 本周（主操作页）

| 元素 | 说明 |
|---|---|
| **本周期目标** | 开周期时自己填（如「这周期着重练胸」）。**填完即锁定，周期内不可改**。修改入口放设置页，默认不用 |
| **本周特殊情况** | 选填：经期 / 出差 / 其他。没有就不填。经期 → 自动下调容量；出差整周空 → 该周不排 |
| **生成本周计划** 按钮 | **每周都要手点一次**（第 2/3/4 周也要）。默认沿用上周模板，按本周情况微调 |
| **计划预览** | 周几 + 训练主题 + 具体动作 + 组数 × 次数 + **重量** |
| **拖动调整** | 整个训练日模块拖到另一天（这周周一有事、下周周二有事，每周都可能不一样） |
| **导入** 按钮 | 确认无误后导入训记 |
| **进度显示** | 本周期第 N/4 周 |

> 用户明确：**每周手动生成 + 手动确认导入**。"因为我要确认一下计划之后再导入，我每周的情况不一样。"

### ② 复盘 · 本周（第二个主操作页）

| 元素 | 说明 |
|---|---|
| **实际完成表格** | 计划 vs 实际，标注完成度（如某动作完成 50%） |
| **每日感受输入框** | 手账式：上面是当天训练内容，下面留方框直接打字。**每天都能写** |
| **AI 复盘 按钮** | 本周未结束时点击 → 提示「本周结束后才可以进行总结」 |
| **复盘结果** | **简短**：这周练得怎么样、有没有达标、有没有完成计划。**不要复杂** |
| 历史复盘 | 留存可回看 |

> **感受只写在这里，不同步回训记。**（用户：我一般不在训练备注里写东西）

### ③ 设置

| 元素 | 说明 |
|---|---|
| **训练日（＝一周几练）** | **点选周几练，「一周几练」就是选中的天数**——不设第二个控件（用户原话：「我选了几个训练日，你就能选几个一周几练」）。初始默认 周一/三/五/周日 |
| **每次时长** | 上下限（初始 60~90 分钟＝1~1.5 小时）。常驻可改 |
| **长期目标** | 如「减脂保肌」。**常驻可改，仅作 AI 参考**，优先级低于周期目标（§5） |
| **体重** | 手动输入，生成趋势图；作为排计划的参考 |
| **基础疾病 / 旧伤** | 如腰突。**仅作背景参考**——陈旧伤已痊愈，不因为腰突就不排用腰的动作 |
| **一周起始日** | 可选周一 / 周日 |
| **用户画像** | 只放一个入口，**点进去才看到内容**，不在设置页铺开 |
| 周期目标修改入口 | 默认锁定，这里是唯一的强行修改口子 |
| **训记接入** | 网页上填 `XUNJI_API_KEY`（写回 `.env`、立即生效、不重启）+ 手动同步两个按钮（「立即同步」增量 /「回补历史」全量）+ 一段说明自动同步是怎么跑的。**排在设置页第一位**——没配 Key 什么数据都拉不到 |
| AI（DeepSeek）配置 | 端点 / 模型 / Key，同一套「网页填 → 写回 `.env` → 立即生效」的逻辑 |

> 以上**全部只放设置页**，不在主页面铺开。

**优先级**：本周特殊情况 > 基础疾病。（急性发作期本来就不会训练，旧伤只是历史背景）

### ④ 数据汇总 —— **本期不做**

- 内容预想：某肌群本周练了多少、哪个肌群训练不够。**但训记 App 自带这些图**
- **后端保留接口，前端不显示入口**（不做一个空白页面给用户）
- 后期用户确定了再说

## 3. 训练画像（核心机制）

### 是什么

一份**由 AI 通读你全部历史后产出的、长期保存的「你的训练情况说明书」**。

类比：**教练第一次带你时做的摸底体检报告。** 之后每周只需看你的新数据，不用重新摸底。

### 里面装什么

- 训练习惯：每周几次、单次多久、实际分化结构（不按标题，按动作肌群聚合）
- 各部位基线：胸 / 背 / 腿 / 臀 / 核心 / 前臂 每周多少有效组，哪些足、哪些长期不足
- 主要动作的当前重量与趋势（例如某个动作停滞了数周）
- 长期存在的问题（例如推拉比例失衡、某部位训练量长期不足）
- 恢复特征：训练时长离散度、实际频率 vs 目标频率

### 怎么用

- 阶段二每次排计划，都把这份说明书一起带上 → AI 立刻知道「你是谁」
- **从此不需要重读原始历史数据**

### 什么时候更新

- 每完成一个周期（或每 N 个周期）重新生成一版
- 复盘结论可以并入画像

## 4. AI 使用策略：一次性画像 + 每周增量

**绝不每次重喂全部历史数据。**

| 阶段 | 频率 | 喂给 AI 的东西 | 数据量 |
|---|---|---|---|
| **阶段一 · 建立画像** | 只做一次 | 过去 3~12 个月完整历史（本地结构化整理后） | 见下 |
| **阶段二 · 每周排计划** | 每周 | 训练画像 + 上周进步 + 各动作趋势 + 薄弱环节 + 本周特殊情况 + 上次复盘 | **目标约 15 KB** |

> **现状（2026-09-30 实测，批次 4 后）**：报告 **66.5 KB ≈ 19,500 tokens**，其中 `candidate_pool`（254 个动作全量目录）**47.7 KB / 71.7%** + `movement_trends`（约 30 条）11.5 KB / 17.3% —— **两项合计 89%**。而一次真正要排的计划只会用到约 15 个动作。
> 现有 analysis 模块的统计能力（当前重量、趋势、周均组数）**全都能复用**，只需把输出目标从「给人看的结论」改成「给 AI 用的摘要」。

> 技术约束：训记读接口限频 30 秒/次，拉一年数据需约 3 小时。库内已有 12 周数据，建议先用 12 周，需要更长的再增量补。

## 5. 关键规则

| 规则 | 内容 |
|---|---|
| **周期长度** | **4 周**（3 周渐进 + 第 4 周减量）。减量周容量减半、强度降 10~15% |
| **生成粒度** | **一周一周生成**。因为不可能提前一个月知道经期、出差这类事 |
| **模板机制** | 一个周期可四周**共用同一模板**；下周计划在**上周模板上微调**，不整体重来。**不需要周期内每次生成新模板** |
| **周期目标** | 周期内**锁定不可改**（防止改来改去等于没目标） |
| **目标优先级** | **周期目标 ＞ 长期目标**。周期目标定这 4 周的焦点（如「着重练胸」），长期目标是背景参考（如「减脂保肌」）。用户明确：「这两个不冲突」——一个周期内可以既保持长期方向、又重点打某个部位 |
| **复盘门槛** | 一周结束才能总结 |
| **重量** | **渐进超负荷是核心**——目标是进步，不是重复排动作。必须给出明确递增（如每周 +1.5 kg 或 +2.5%） |
| **达标判定** | 用户练不动会自然反映在训记历史里（该动作不再出现那个重量）→ 系统**对比计划 vs 实际**调整下次递增 |
| **新动作** | **不追求每次推新动作**。「我们的目的是更好的训练」 |
| **旧伤** | 只作参考，不自动禁用相关动作 |
| **确认机制** | 保留两道：生成 → 我确认 → 导入训记。**每周手动导入** |

## 10. 阶段二：要补的功能（V1~V9）

### 10.0 ⚠️ 先纠正一个前提：「一周几练 + 每次时长」**已经存在于代码里**

用户新提的需求（设置里配一周几练、每次多久，作为常驻基础值供 AI 默认使用）——**不是新建功能，是接线**。链路已全部就绪：

### 10.2 建议执行顺序与理由

```
V1 设置页·训练基础   ← 零依赖、工作量最小，且后续每次生成都吃它，先把它修对
  └→ V2 周期 + 周期目标
       └→ V3 本地摘要层（训练画像）   ← 真正决定 AI 排得好不好的一步
            └→ V4 接 DeepSeek + 第一次真跑
                 └→ V6 计划 vs 实际 ←→ V5 增重策略   （两者互相咬合，一起做）
                      ├→ V7 调整训练日
                      └→ V8 复盘页
V9 身体信息 + 画像入口   ← 与上面全部低耦合，任何时候插进来都行
```

**为什么 V3 一定要在 V4 前面**：现在喂 AI 的报告 **66.5 KB ≈ 19,500 tokens**，其中 `candidate_pool`（254 个动作全量目录）47.7 KB / 71.7% + `movement_trends`（约 30 条）11.5 KB / 17.3%，**合计 89%**——而一次真正要排的计划只会用到约 15 个动作。现在接 DeepSeek 等于教它读一份马上要扔掉的材料，prompt / validator / 失败降级全要返工。
反方向不成立：摘要层要放什么由你的诉求决定（动作 / 当前重量 / 趋势 / 薄弱环节 / 该练没练到），**跟模型是谁无关**，所以先做 V3 零风险。

### 10.3 各步要点（实现备忘）

**V1 · 设置页训练基础**
- 后端现在**完全没有 `user_goal` 的写入路径** → 新增 `GET /api/goal` + `PUT /api/goal`
- ⚠️ 写入语义：`user_goal` 是**带 `effective_from` 的历史表**（有 `idx_goal_active` 索引 + `plan.goal_id` 外键）→ 改设置应当 **INSERT 新行 + 旧行 `is_active=0`**，不要 UPDATE 旧行。这样历史计划的 `goal_id` 仍指向当时的目标，语义正确
- 「训练日」多选必须与「一周几练」**数量联动**（选 4 练就只能勾 4 天）——这是修掉 §10.0 那个矛盾的根治办法
- `analyze.ts:29` 的种子同步修正：`45/90 → 60/90`、`[1,3,5]` 与次数对齐

**V2 · 周期 + 周期目标**
- 新表 `training_cycle`：`cycle_no / start_date / end_date / goal_text / status`
- ⚠️ **别和 `user_goal.goal_type` 混名**：`goal_type` 是长期方向（减脂保肌 / 增肌 / 力量），周期目标是"这 4 周的焦点"（着重练胸）。**两者都要进 AI 输入，但语义不同**
- 周期目标周期内锁定；设置页留唯一「强行修改」入口（默认不用）
- 第 4 周自动判为减量周：容量减半、强度降 10~15%
- 「本周特殊情况」（经期 / 出差）是**单周字段**，不属于周期

**V3 · 本地摘要层**
- `candidate_pool`：254 个动作全量 → 只给这套计划相关的 **20~30 个**（历史练过 + 肌群覆盖 + 白名单过滤）
- `movement_trends`：约 30 条 → 只留近期在练且有数据的 ~15 条，每条压成一行
- 产出两件东西：① **训练画像**（长期、N 周一版、`§3` 定义的内容）② **周摘要**（画像 + 上周变化 + 待补部位 + 本周特殊情况 + 上次复盘结论）
- **复用不重写**：`server/analysis/` 统计能力全保留，只换输出目标（精简 `reportSchema` + 新增 `summarySchema`）

**V4 · 接 DeepSeek**
- `.env.example` 补 `LLM_MODE / LLM_BASE_URL / LLM_API_KEY / LLM_MODEL`；默认模式 `workbuddy → http`
- 🔴 **Key 只能进 `.env`**（安全红线）。设置页表单若允许填 Key，必须**写回 .env 文件**，不得入库
- 第一次真跑重点验证：JSON 输出稳定性、中文 prompt 遵从度、超时行为

**V5 + V6 · 增重策略 + 计划 vs 实际**（一起做）
- 递增在**本地先算好**（当前重量 + 建议递增 + 依据），AI 只做裁决与例外处理
- 第 4 周减量：重量不变或 −10%
- V6 反哺 V5：训记里该动作没出现那个重量 → 说明没达成 → 下次不递增或回退
- **这是整个闭环的关键**，也是「渐进超负荷」真正落地的地方

**V7 · 调整训练日**
- 建议先做**「移动按钮」而不是拖拽**：功能等价（整个训练日模块挪到另一天），触控/移动端更可靠、零新依赖。要真拖拽再迭代
- 后端：`plan_day` 换 `datestr` + 事务内重排 `ord`
- **目标日已被占用 → 交换**（实现时补的语义）：一周 3 练最常见的操作是「周三有事，和周五换一下」，只允许挪到空日得挪两次。交换走中间态日期 `0001-01-01` 避开 `UNIQUE(plan_id, datestr)`（`ord` 没有唯一约束，可自由重排）

**V8 · 复盘页**
- 手账式：上=当天实际训练表格，下=感受输入框。**每天可写，一周一次总结**
- 新表 `daily_note`（`datestr / text`）；感受**只存这里，不同步回训记**（§6 决策 1）
- 「AI 复盘」按钮：周未结束 → 提示「本周结束后才可以进行总结」
- 输出必须**简短**：达标吗 / 完成率 / 下周微调。结论进 V3 的周摘要 → 闭合成环
- **实现时补的三条**：
  ① 周级数字**复用 V6 的 `loadPlanActual`**（排计划时 AI 看的就是它），复盘页与 AI 不会各说一套；
  逐日完成度只统计 `catalog_id` 非空的计划条目，与该口径一致。
  ② **「今天」不算欠账**：`loadPlanActual.missed_days` 会把今天与未来计划日一并算作漏练，
  手账页周中打开会看到一串红色「没练」。所以逐日 status 把「今天且尚无有效组」判为 `upcoming`，
  而 `missed_days` 改由 status 派生（只含已过去且确实没练的日子）。周已结束时两者等价。
  ③ 周复盘**不给分析报告**（只给一周事实 + 用户感受）—— 给了只会让输出变长，与「必须简短」冲突。

**V9 · 身体信息 + 画像入口**
- 体重：手动输入 + 趋势图；旧伤/基础疾病：**只作背景参考，不自动禁用相关动作**（§5 旧伤规则）
- 「用户画像」入口：只放一个入口，**点进去才展开**（§6 决策 6）

实现纪要：
① **体重与时序、旧伤与文本分两处存**：体重进 `weight_log`（schema v6，一行一天、同日覆写、可补记过去、可用
`weight_kg: null` 删掉填错的那天）；旧伤进 `app_config['body_info']` —— 它是一段长期有效的自由文本，
没有「什么时候写下这句话」的时序含义，跟体重挤一张表只会让人误以为它有时效性。
② 🔴 **旧伤只进文本，不进任何筛选逻辑**：`digest.profile.body.conditions` 是它进入 AI 输入的唯一路径，
prompt 里明确写了「不得据此禁用、替换或减少任何动作」。有专门的用例守着这条红线 ——
填入旧伤前后的 `constraints` / `candidate_pool` / `week` / `findings` 必须**逐字节相同**，
只有 `profile.body` 变。优先级仍是：本周特殊情况（`week.special_note`）> 基础疾病。
③ **画像 = 系统实际喂给 AI 的长期画像**，与排计划走同一条 `buildPlanDigest` 装配路径 ——
页面看到的和 AI 看到的是同一份，用户点进来是为了**核对**。它是本地统计出来的，不是 AI 写的
（§3 旧描述「AI 通读全部历史产出说明书」在 V3 改成本地摘要层之后就不成立了）。
④ 画像**折叠时不发请求**：`useProfile(enabled)` 由「展开查看」按钮控制 ——
画像要现场拼一遍 digest，设置页每次打开都白算一遍没有意义。

### 11.1 先澄清：「舍弃」的是什么

批次 2 砍的是 **C3 六个疲劳代理信号（S1~S6）**，也就是「**没有 RPE 时用代理指标猜疲劳**」。
**RPE 本身从来没有被舍弃，全链路都还在**，而且实测结果是——它是一条**恒为 null 的死链路**：

| 报告 `movement_trends[].delta_rpe` | 恒 `null` | 约 30 条全 null |
| 报告 `window.last_session.movements[].avg_rpe` | 恒 `null` | 10 条全 null |
| 规则 R-AG-06（动作疲劳累积） | **死分支**，覆盖率 0 时永不触发 | — |
| 规则 R-AG-15（RPE 缺失提示） | **每次必命中** | 每次报告都刷一条「你该记 RPE 了」 |
| AI prompt（`planGenerator.md:32`） | 要求 AI 输出 rpe：主项 7~9、辅助 6~8 | — |
| `plan_exercise.rpe` + `template.ts:134` | 模板硬编码 `rpe: isMain ? 8 : 7` | — |
| **写回训记**（`xunji/writer.ts:127`） | `if (ex.rpe !== null) s.rpe = String(ex.rpe)` | 🔴 **AI 编的 RPE 会被写进训记** |

> 顺带一个自相矛盾：`writer.ts:157` 的注释写着「rpe 不算训练内容（Q29 结论）」——我们自己的校验器不把 RPE 当训练内容，却又把它写进训记。

### 11.2 问题不在"还有"，在"不闭环"

RPE 的真正问题是：**AI 给你定 RPE → 写进训记 → 你不看、不验证、下次调整也用不上。**
这跟「重量必须能靠训记历史闭环校正」（§5）正好相反——**它是一个没有反馈回路的数字。**

### 11.3 建议的三层处置

| 层 | 处置 | 理由 |
|---|---|---|
| **读取**（`train_set.rpe` 列 / parser / `xunji/types`） | **保留** | 训记 API 本来就会返回；删列要建迁移；哪天你开始记，历史不丢 |
| **报告与规则**（`delta_rpe` / `avg_rpe` / `rpe_coverage` / `warnings` / R-AG-06 / R-AG-15） | **删** | 恒 null 的字段是纯噪声；R-AG-15 每次必命中＝永远在刷「你该记 RPE」；**在 V3 重写报告输出时顺手清掉，零额外成本** |
| **计划层**（AI 输出 rpe / 模板硬编码 7~8 / 写回训记的 rpe） | **待用户拍板** | 见 §11.4 |

> `plan_exercise.rpe` 列本身可以留着不删——同 §9.1 的理由，删列要迁移、收益为零。
